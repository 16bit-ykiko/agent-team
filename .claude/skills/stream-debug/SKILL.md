# Stream debugging

Fixtures for every fact below live in `service/tests/snap/claude/`, `codex/`, `cursor/` and `agy/` (capture-sdk skill); the `.snap.md` next to each recording is the transcript the pipeline produces from it.

Pipeline: SDK frames → `service/src/session/claude.ts` (frames → `StreamEvent`) → `service/src/workspace/workspace.ts` (`Workspace.applyInnerEvent`, message list, `contentOffset`) → WebSocket `stream_event` batches → `webview/src/state/stream.ts` (`applyEventsToMessage`, same aggregation client-side) → `webview/src/chat/events.ts` (`timelineBlocks`, `foldSubagents`) → `webview/src/chat/messages.tsx`. The server and client aggregations must produce the same transcript; `service/tests/snap/snap.test.ts` asserts that on every recorded fixture. Codex goes through `session/codex.ts`, Cursor through `session/cursor.ts`, agy through `session/agy.ts`, into the same event model.

## Frame facts (from recordings, not docs)

- **Quick Bash**: `assistant` tool_use → `user` tool_result. No task frames.
- **Run times** are our clock: a tool call from its tool_use (`startedAt`, set by every backend's session, so a call still running counts up in its row and, after 3 s, in the message header when the backend names no activity of its own) to its tool_result (`durationMs`, merged into the call), a task from the call that started it to its `task_notification` (`subagent.durationMs`). A foreground command's `task_started` comes only after it has run a few seconds (fixture `claude/bash-long`), so a task never starts its clock there. The CLI's `usage.duration_ms` on agents counts from the first run, a resumed agent's idle time included.
- **Long foreground Bash** (a few seconds or more): CLI still emits `system/task_started` with `is_backgrounded: false`, then `task_notification`. This is _not_ a background task — no card. Cards for non-agent tasks only when `is_backgrounded === true`, or a later `task_updated` patch sets it, or the task appears in `background_tasks_changed`.
- **Background Bash** (`run_in_background`): `system/background_tasks_changed` arrives **before** `task_started`. Card = the command (from the tool_use input, keyed by tool_use id), tool_use stays in the folded tools box.
- **Background completion**: the CLI starts a _new turn_ with a second `system/init` and no user frame; a `task_notification` carries the summary. That is a wake-up (banner `wakeup`), not a new user message.
- **Resume after a restart with an orphaned background task** (fixture `claude/resume-orphan-bg`, after its `end` step): the CLI emits `task_notification` (status `stopped`, unknown task id) _before_ `system/init`, then a phantom `result` with `num_turns: 0`, `origin: {kind: "task-notification"}`, then a second `init` and the real turn. That result must not end our turn (`handleResult` skips it while `expectingTurn && awaitingFirstOutput`), or the prompt renders as "no output" and the reply as a wake-up. Real results never carry `origin`.
- **Agent (Task tool)**: `task_started` with `task_type: "agent"` / `subagent_type`; agents always get a card, and the card replaces the spawning tool_use (`spawnToolUseIds`). Subagent frames carry `parent_tool_use_id`; depth-2 frames carry the child's tool_use id, so the session wraps them per ancestor (`wrapToRoot`) as `subagent_progress` carriers with `_innerEvent`. Both aggregations recurse into nested carriers.
- **Agent resumed by SendMessage** (fixture `claude/resumed-agent-bg`): a finished agent sent a message gets a second `task_started` with the _same_ task id but the SendMessage call's `tool_use_id` (so do its `task_progress`/`task_notification`), while its own `assistant`/`user` frames still carry the _original_ Agent call's id as `parent_tool_use_id`. The session keeps that first id per task (`agentSpawnToolUse`) to route them. A background shell the subagent starts has `owned_by_subagent: true` and no parent field; only its tool_use (seen in the subagent's frames) ties it to the card.
- **Slash skill typed by the user** (`/hello`): no user frame at all. **Skill tool called by the model**: a `user` frame with `isSynthetic: true` containing the skill text — treat as a `skill` notice, never as a wake-up or a new user turn. `shouldQuery: false` frames append to the transcript without starting a turn.
- **Wake-up detection** (`session/claude.ts`): a user-shaped frame counts as a wake-up only when not processing, or while expecting a turn before any first output (`awaitingFirstOutput`), and it is not a tool_result, not synthetic, not `shouldQuery === false`.
- **Usage limit** (fixture `claude/usage-limit`, recorded against a local stand-in API): the first refused request brings a `rate_limit_event` (`status: "rejected"`, `rateLimitType`, `resetsAt`), here before the turn's `system/init`; every refused turn then ends in a synthetic `assistant` frame (`error: "rate_limit"`, `is_api_error_message: true`, model `<synthetic>`, text "You've hit your session limit · resets 2:40am (…)") and a `result` with `subtype: "success"`, `is_error: true`, `api_error_status: 429`. Do not count on a `rate_limit_event` per turn: the second refused turn of the fixture, 0.8 s later, had none (the CLI sends it when the limit changes, throttled). So `ClaudeSession.refused` reports each refused turn from its API-error message, and the event only says whether a usage limit stands: the CLI marks any 429 `rate_limit` (throttling, load), and with no rejection standing that is a plain error.
- **Init frame** (Claude): carries `effort` and `fast_mode_state`; `/fast` sets `settings.fastMode`; warn when the state is not `on`.
- **Context stats**: from the last main-loop assistant `usage` (not the cumulative result usage). Codex: from the last `thread/tokenUsage/updated` (one after every request: `last.totalTokens - last.reasoningOutputTokens` over `modelContextWindow`, the window less codex's reserve).
- **Codex** (fixtures `codex/*`, `codex app-server` over JSON-RPC, `session/codex.ts`): one process per session holds the thread; a turn runs from `turn/start` to `turn/completed` (status `completed`, `interrupted` or `failed`), every notification naming its `threadId`. The turn's own prompt comes back as its first `userMessage` item. Text streams as `item/agentMessage/delta`, several agent messages a turn being paragraphs of one reply; reasoning only with `summary: "detailed"` (gpt-6 models default to none), as `item/reasoning/summaryTextDelta`. Commands are `commandExecution` items (`/bin/bash -lc '…'`, the bare command in `commandActions`) with `aggregatedOutput`, `exitCode` and codex's own `durationMs`; output printed before the item started is lost from the deltas and the aggregate (`commands`: "line 1"). Client-defined tools (`dynamicTools` at `thread/start`, kept across `thread/resume`) arrive as a `dynamicToolCall` item plus an `item/tool/call` request we answer; `success: false` fails the item (`tools`).
- **Codex subagents** (`codex/tools`): a `subAgentActivity` item (`started`, `interacted`, `completed`) on our thread names the subagent's `agentThreadId`; that thread's turns and items arrive on the same connection under its id. Subagents do not get the client-defined tools.
- **Codex steer and stop** (`codex/steer`, `codex/interrupt`): `turn/steer` answers at once; the model reads the message at its next request, where a `userMessage` item appears in the running turn, carrying the `clientUserMessageId` we sent as its `clientId`. Nothing can be steered before the turn's id is known (turn/start answered): the session holds such a steer until then. `turn/interrupt` ends the turn within milliseconds as `interrupted` and leaves the process up. The running command is not killed: its output and `item/completed` come later, during whatever turn runs then, under its old item id (`codex/steer-interrupt`), so its card is closed at the interrupt and the late completion ignored. A steered message the model had not read yet is dropped with the turn (same fixture): the panel runs it as the next turn. A plain 429 is an `error` with `codexErrorInfo.responseTooManyFailedAttempts` once codex gave up retrying (`willRetry: false`).
- **Codex usage limit** (`codex/usage-limit`, local stand-in): every refused turn brings `account/rateLimits/updated` (the spent window at `usedPercent` 100 with its `resetsAt`), then `error` with `codexErrorInfo: "usageLimitExceeded"`, then `turn/completed` `failed`. Rate-limit updates also follow every request; the protocol documents them as sparse (a missing window keeps the last one seen).
- **Codex at capacity** (no fixture: it cannot be brought on; seen in the rollouts under `~/.codex/sessions`): the turn ends `failed` with `codexErrorInfo: "serverOverloaded"` ("Selected model is at capacity. Please try a different model.", `server_overloaded` in the rollout), often minutes in and after work, and codex does not retry it. The prompt is already in the thread by then. The session keeps the panel's turn going: a `retry` banner, then after 5 s … 2 min a new `turn/start` asking the model to carry on, at most five times. Steers the failed turn had not read go back to the queue, and none is taken during the wait; Stop ends the turn; a compaction is not retried.
- **Codex resume and compaction** (`codex/resume`): a new process resumes the thread by id with its history and tools (the developer instructions are in its rollout too, so neither goes in again). Probed without a turn, not recorded: a thread `codex exec` started resumes as well, and a missing one is a `-32600` "no rollout found for thread id …". `thread/compact/start` runs as a turn of its own with a `contextCompaction` item.
- **Cursor** (fixtures `cursor/*`, `@cursor/sdk` 1.2.0 local runtime): the session reads only onDelta updates; `run.stream()` repeats them one for one (text and thinking per delta, `tool_call` running/completed) and `run.wait()` gives the end (`finished` with `result`, `error` with `error`, `cancelled`). A new agent's first run starts 5–25 s after `send` (agent creation, workspace scan); a warm one's in ~20 ms. Per block `thinking-delta`… then `thinking-completed` with its duration; `text-delta`; `tool-call-started`/`tool-call-completed` by `callId` with the typed call (`{type, args, result: {status, value | error}}`), parallel calls completing out of order; `partial-tool-call` comes too (ignored). The SDK's converter (`dist/esm/336.js`) drops some sixty of the runtime's tool types outright, `awaitToolCall` (Await/AwaitShell), web search and fetch, `GetDynamicTools` among them: only `tool-requests-listed` counts them, with the shown calls of the same step, whose starts all come before it. The session shows the rest as a `Cursor` card once the agent has waited on them `HIDDEN_CALL_SHOWN_MS` with no shown call open, closed by the next activity (timed, so `cursor-session.test.ts`, not the replay). A shell sent to the background (`block_until_ms: 0`) has no `timeout` in its args and completes at once, empty (`cursor/background-shell`); its output is in `~/.cursor/projects/<cwd slug>/terminals/<id>.txt`, and the runtime's own transcript of every call, hidden ones included, in `…/agent-transcripts/<agent id>/<agent id>.jsonl`. Edits, new files included, are `edit` calls with only `path`; the unified diff (`diffString`) comes with completion. A 3 s foreground shell sent no `shell-output-delta`: stdout/stderr/exitCode come with completion. `turn-ended` usage sums the turn's model calls and its `inputTokens` include `cacheReadTokens` (`totalTokens` = input + output): no context figure. Stop = `run.cancel()`: `cancelled` at once, the running call never completes (the session closes it as "Interrupted"), no usage; the next send runs at once on the same agent. A custom tool is an `mcp` call from provider `custom-user-tools`; its `context.sessionId` is the agent id in the main loop; a thrown error reaches the stream as "Tool execution error" only, a returned `{content, isError: true}` as a `success` whose value has `isError` and the text (`cursor/custom-tool-refused`). A subagent is a `task` call (`args.description`, `prompt`, `subagentType`, `model`); its own thinking, text and tool calls arrive as `tool-call-delta` updates of that call (`taskUpdate`, one level only), and its completion's value carries `conversationSteps`, `isBackground`, `durationMs` (`cursor/subagent`): the session makes it a card like a Claude agent's. There is no `ls` tool (the model globs instead); grep's content matches can come without line or number (`cursor/local-tools`). Web search and fetch run but never appear: nothing but `tool-requests-listed`, and `run.conversation()` leaves them out too (`cursor/web-tools`). Cursor refuses Google's models (Gemini) by the region its traffic leaves from: the run ends `error` "This model provider is not supported in your region" (here mihomo sends cursor.sh and cursor.com through its AI group for that). A bad model id: `Agent.create` throws `ConfigurationError` after ~2 min. The read tool shows the model an image (result content `""`). Behind `HTTPS_PROXY` the SDK needs HTTP/1.1 (`useHttp1ForAgent`) and `http.setGlobalProxyFromEnv()`; its HTTP/2 stream ignores proxies.
- **agy** (fixtures `agy/*`, `agy acp` 1.5.8, which updates itself: ACP v1, JSON-RPC 2.0 over stdio, `session/agy.ts` on `codex-rpc.ts`'s client): one process per session holds the conversation, run with `--dangerously-skip-permissions` (no `session/request_permission` comes) and `--log-file` (see below). `session/new` (no model call) returns `configOptions` `model` / `thought_level` / `mode`, set with `session/set_config_option` (switching the model resets the level to the model's default, so the level is set after it). A turn is one `session/prompt` until its response: `stopReason` (`end_turn`, `cancelled` after a `session/cancel` notification, `refusal`, `max_tokens`, `max_turn_requests`) and `usage`, which sums the turn's model calls (agy/turn: 44649 input over five calls); the context is the last `usage_update` {used, size} (1.5.8+, after each model call and in a load's replay; Flash's size 1048576). Updates arrive as `session/update` notifications, only while a prompt or a load runs: the prompt echoed first as `user_message_chunk`, text as `agent_message_chunk` pieces, `tool_call` (in_progress) then `tool_call_update` (completed/failed) by `toolCallId`, each with agy's own `name` and `args` (plus a `toolSummary` agy adds to every call) beside ACP's `kind`/`title`/`rawInput`: `run_command` {CommandLine, WaitMsBeforeAsync} with `rawOutput` {output: "[Created At: …\nCompleted At: …\n]Command exited with code 0.\n\nCommand output:\n<out>\r\n", exit_code}; `write_file` {Path, Content} and `edit_file` {Path, Target, Replacement} with a `diff` content of the whole file; `manage_task` {Action: status, TaskId "<conversation>/task-N"}; `invoke_subagent` {Prompt, Role, TypeName, Model} (`/teamwork` makes one): it completes at once without a result and the subagent works in a conversation of its own, streaming nothing; `session/list` leaves subagents out, but `session/load` of the subagent's id replays its conversation, and agy's store names the id (`conversations/<id>.db`, whose step 0 holds the spawning call id: `agy-store.ts`), so the session loads it with the main one and fills the card (its messages by count and calls by id: agy folds a subagent's thoughts between loads, so they are left out); a subagent reports back with `send_message` {Message, Recipient: the parent's id}, which wakes the parent, and its card closes once that report is in and nothing of it is open (agy/subagent; `TypeName` "self" for one like the agent, `DeepCoder`/`DeepInvestigator` built in); subagents live in their agy process and end with it; `ask_question` {questions: [{question, options, is_multi_select}]}: pending until answered, and over ACP only an elicitation (a client capability the panel does not declare) answers it: a prompt sent meanwhile gets the question back as text without a model call and is dropped, the next gets nothing; a new agy process has no question waiting (the session restarts it to send the answer when nothing runs in the background there), and the panel's appended instructions tell agy not to call it (verified: `/teamwork`'s interview then comes as plain text); an MCP tool as `mcp_<server>_<tool>`, its update carrying no result (the session takes it from its own MCP server). Stop (`session/cancel`) ends a running command: a `tool_call_update` `failed` with empty output, then `cancelled` (agy/interrupt). A slash command's prompt echoes without the command (` Create the file…` for `/teamwork Create the file…`); a load replays it as two user chunks. The panel's tools: a stdio MCP server in `session/new`/`resume`/`load` `mcpServers` (agy asks `server/discover`, then `initialize`, `tools/list`; a load with the same list spawns none again); its instructions: `_meta.antigravity.systemPrompt.append`. Flash at thought level low streams no thoughts.
- **agy background commands** (`agy/background`): a command still running after `WaitMsBeforeAsync` goes to the background and its call stays `in_progress` past `end_turn` (the session gives it a `local_bash` card and waits). About 2 s after it exits agy wakes by itself (a model call; its log names each one, `streamGenerateContent`, as it ends, the reply stored by then) and works while idle, streaming nothing. A command agy runs is `bash -c <CommandLine>`, a child of `agy acp` leading a process group of its own on a terminal: the card's Stop ends that group. `session/load` (no model call) replays the conversation as stored: one chunk per message (a reply whole), each call once in its latest state, a call still running in the background listed first, ahead of the first user message, in its place once it ended. The session loads after every turn (the baseline), before a prompt when agy may have worked since the last load (its log showed a model call while idle, a call of agy's is open, a reply to a command's end is awaited, the load after the last turn failed, or no log is watched; what it did comes first in that reply, and the load after the turn tells the turn's own items from the rest), when the log has shown a model call and been quiet 3 s (then 10 s later, and up to six times more after a command's end until agy's reply to it), and every 60 s while a command runs; calls by id and messages in order give what is new: a turn of its own under a `wakeup` banner. A load during agy's own turn answers in ~2 s. A prompt sent then waits for agy's current model call (~5 s), then runs; the rest of agy's own turn lands after the reply. `session/resume` replays nothing (and works in a fresh process); resuming an id agy lacks fails -32603 "Failed to read session …; retry, or load it with session/load", and a load of such an id starts an empty conversation.
- **Stop = interrupt** (fixture `claude/interrupt-bg`; `perTaskStopAffordance` declared in the query options): the foreground command gets a `task_notification` (stopped), then its `tool_result`, a user text "[Request interrupted by user for tool use]" and `result/error_during_execution`. The process lives on, and so do background shells and agents. Because we asked for it, `ClaudeSession` turns that error result into a `result` with `interrupted: true`, which the workspace renders as `*[interrupted]*`, not as an error.
- **stop_task** on a background task: `background_tasks_changed` (without it), `task_updated` (status killed), `task_notification` (stopped). A stopped background agent then reports back like any finished task: a wake-up turn whose result has `origin: {kind: "task-notification"}`.
- **Stop before any output** (fixture `claude/interrupt-early`): after `system/init` and before `message_start`, an interrupt yields a plain user text "[Request interrupted by user]", then `result/error_during_execution`. Arriving while we await the first output, that frame would read as a /skill expansion; `ClaudeSession` drops it while an interrupt is pending.
- **Wake-ups survive an idle interrupt** (fixture `claude/wakeup-interrupt`): a scheduled wake-up is no task, and interrupting with no turn running leaves it pending. It fires. Cancelling one therefore closes the CLI process (`cancelWake`); the session resumes on the next message. Its time comes from the `ScheduleWakeup` tool result ("Next wakeup scheduled for 12:51:00 (in 93s)"): the CLI rounds up to a minute boundary. A call whose result is an error schedules nothing; a new one replaces the pending one, `stop: true` or "Wakeup not scheduled" (the loop's age limit) leaves none.
- **A fired wake-up** (fixture `claude/wakeup-bg`) opens its turn with a `command_lifecycle` frame (`state: "started"`, `wakeup_source: "loop_wakeup"`, `scheduled_for`: the time it was for) before `system/init`, and closes it with `state: "completed"` after the result. The `ScheduleWakeup` result frame carries that time as `tool_use_result.scheduledFor`. Our prompts carry no uuid and get no lifecycle; a task-notification turn gets none either (its result has `origin.kind: "task-notification"`); other commands of the CLI's own (auto-continuations) have no `wakeup_source`. The session takes `started` as the turn's start, so a message sent before the first output queues behind it, and as the wake-up firing only when `scheduled_for` is the pending one's (a fire that waited behind a turn leaves the newer one that turn scheduled). Turns the user or a task's report starts leave the wake-up pending. CLI 2.1.299+ fires it while background tasks run; 2.1.280 held it until every one had ended (its drain loop counted waiting for them as busy), usually long enough for the model to reschedule it away. Only when the process that held it is gone (a crash) does the workspace send its prompt itself, at its time, after the agent's queue (`wakeDue`, `takeWake`); a live process fires it, however late, and sending it too would run it twice. The CLI re-arms a wake-up on resume only for background jobs (a job dir), not for SDK sessions.
- `step` is per content block, not per model step — never split step boxes on it.

## Event model

- `StreamEvent.kind`: `text_delta`, `thinking`, `tool_use`/`tool_result` (paired by `toolUseId`), `subagent_start`/`subagent_progress`/`subagent_done` (`subagent.taskId`, `taskType`, `description`, `prompt`, `_innerEvent` carrier), `notice` (levels incl. `wakeup`, `schedule`, `skill`), `retry`, `compact`, `error`, `result`, `usage`.
- `contentOffset`: where in the message text the event sits, so tools/steps interleave with prose. Missing offset → previous event's; no offsets at all → everything at 0 (legacy messages).
- **Cards** are only for agent tasks and backgrounded tasks (`taskType`); they are timeline boundaries (`timelineBlocks`) so step boxes split around them. Everything else lives in the folded step box.
- **Banners** (`BANNER_KINDS`): compact, notice, retry, error. Long ones fold (`bannerFolds`); truncated content records `contentLength` and is fetched on demand.
- **Summary pages**: the server sends `summarizeMessages` (`detail: "summary"`, 600-char cap) for history; details load lazily. On reconnect `mergeLatestPage` keeps the richer version; `downgradedMessageIds` triggers re-fetch so live messages never show "tap to load".
- **Steered messages** (Codex): a message sent while a turn runs is handed to it (`Workspace.steer`) and stays queued, flagged `steering` (not cancellable, skipped by the queue), until the model reads it: the session then emits `steered` with the panel message id, and the workspace settles the reply so far (drops it if still empty) and opens a new one under that message. A turn that ends without reading it emits `unread`, and a restart clears the flag: the queue runs it as a turn of its own. No `StreamEvent` marks any of it: the client sees the messages change.
- **Normalisation** (`normalizeEvents` in workspace/workspace.ts): on load, missing content → "", running/status-less messages → stopped.

## Debugging recipe

1. Find the fixture that matches the symptom (`ls service/tests/snap/{claude,codex,cursor}`, read the `.snap.md`); `npm run summarize -- <jsonl>` for the frames. None matches → capture-sdk skill.
2. Reproduce in the replay test (assert the expected card/banner/pairing), watch it fail.
3. Fix on the server side first; if the client aggregation now disagrees, fix it to match — never fork the logic.
4. UI: `webview/tests/events.test.ts` for block splitting, `components.test.tsx`/`ui.test.tsx` for rendering. A screenshot bug gets a test that renders the same events.
